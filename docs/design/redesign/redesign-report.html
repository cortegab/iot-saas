Redesign review: structure, CRUD and three directions

The frontend already has good bones: a real token system in globals.css and 23 shared primitives. It feels unstructured because many pages build their own UI instead of using those primitives, a few key primitives are missing, and the catalog CRUD has bugs users can see. This page lists what to fix and links three interactive directions to choose from.

Audit of frontend/src and backend/src/app · 29 Sep 2026

At a glance

Consistency is the main gap

18 copies of one field-label style, 4 copies of the one-time secret box, 5 section-label variants, 3 error styles.

5 P0 CRUD defects

They cause wrong data, a security hole, or broken MQTT topics. Four come from the device-template catalog and one from tenant roles.

9 missing primitives

Toast, Dialog, Sheet, Switch, CopyField, SecretReveal, InlineEdit, DataTable and a filled danger Button. Every demo uses all of them.

Where to improve

Grouped by what a user notices. File paths are relative to frontend/src.

Shell and navigation

  • The logo, post-login redirect and auth redirect all go to /devices, but Dashboards is the first nav item.
  • The current workspace is only visible inside the user menu, and the tenant switcher is a native <select>.
  • There's no max content width, so tables stretch on wide screens. Create pages set their own max-w-*.
  • The realtime badge disappears when the sidebar collapses and never shows on mobile.
  • Nav has one unlabelled group plus "Configure". Rules and Notifications have no clear place.

Fix: labelled groups (Monitor, Automate, Configure, Admin), a workspace chip at the top, breadcrumbs in the header, ⌘K search, and a max-w content column.

Design system usage

  • The field-label recipe is copied 18 times in sentence case, while Field uses uppercase. That makes two form styles.
  • The one-time secret box is copied 4 times with different copy and dismiss behaviour (devices/page.tsx:154, devices/new/page.tsx:151, devices/[deviceId]/page.tsx:709, settings/tokens/page.tsx:148).
  • Inline rename is built 4 ways. Copy-to-clipboard is built about 6 times. Pill toggles rebuild SegmentedControl 3 times.
  • Button has no filled danger variant, so ConfirmDialog hand-builds one.
  • Raw values bypass tokens: text-white, text-[10px], and chart skeletons at both 260px and 300px.

Fix: add the 9 primitives below, and add a lint rule (or review checklist) against raw label, card and button class strings in app/.

Page structure

  • Device detail uses breadcrumbs; every other detail page uses a back link. The rule detail title is the generic "Edit rule".
  • devices/new, login and register hand-build cards and headings instead of using PageHeader.
  • Members, API keys and roles are card lists; everything else is a Table.
  • Button labels mix case: "Add Dashboard", "Create Rule", "Regenerate Credentials".
  • Settings sub-pages share one header and have no title or description of their own.

Fix: one page template (breadcrumb, title, lede, primary action), every list as a DataTable, and sentence-case labels throughout.

Feedback states

  • There's no loading.tsx, error.tsx or not-found.tsx. The shell loader is a bare "Loading…".
  • There are no toasts. Success is silent, and several mutations fail silently (template and device enable/disable, regenerate credentials).
  • The dashboard detail page shows a skeleton forever when the request fails (dashboards/[dashboardId]/page.tsx:193).
  • Users and Tokens show the error box and the empty state together.
  • No page guards unsaved changes.

Fix: route-level boundaries, toasts with Undo, the right loading/empty/error state for each case, and a dirty-state save bar with a leave guard.

Permissions in the UI

  • Admin-only actions are shown to viewers and fail with a 403: Add device, Regenerate, template edit, rule editor, device settings.
  • Dashboards are gated the other way round: the backend lets any member manage their own, but the UI hides this behind isAdmin.
  • The API tokens tab is visible to non-admins, who then see "Admins only".

Fix: a single can(action) helper that mirrors the backend dependencies. Hide what the user can't do and show a read-only banner. Try "Viewer" in any demo's controls.

Accessibility

  • Many hand-built buttons have no focus-visible style. The widget remove button is a text "×".
  • Tabs hardcodes aria-label="Sections". Tooltips are native title=.
  • With no toasts there's no aria-live region, so screen readers never hear results.

Fix: primitives own focus and ARIA. The demos use polite live regions, focus-trapped dialogs, role="switch" and aria-sort.

"Metric catalog" and "actuator catalog" aren't separate entities. They are JSONB arrays inside a device template (DeviceCatalogEntry). The unit catalog is a frontend-only list in lib/units.ts. There is no sites/locations entity.

Three directions

All three use the same mock workspace (Northfield Greenhouses: 15 devices, 4 templates) and the same behaviour, so you can compare them directly. Each demo has a "Demo controls" panel in the bottom-left corner for switching role and list state and for simulating a 422 on save.

Keeps today's identity: dark first, brass for controls, orange for data, Chivo + IBM Plex. Adds structure around it.

  • Grouped sidebar with counts, workspace chip, breadcrumbs
  • Template editing in a side Sheet with tab error badges
  • Detail pages: readouts and trend, with a rail for controls, rules, credentials and manage

E · The whole site on D, with the review fixes applied

Every section is built: Dashboards, Devices and device detail, Notifications, Rules with Failed deliveries, Device templates, Members, API keys and Workspace settings. The same rule applies everywhere: configuration records (template, rule, member, API key, add or edit a device) open in a panel. The panel docks beside its own list and opens as a drawer over any other page. Operational views (dashboards, device detail, notifications) are full pages. The review's other fixes are also in place:

  • Metric and actuator rows collapse to one line, one expanded at a time.
  • Actions sit in a sticky panel footer.
  • Saving asks for confirmation only when the change breaks rules or widgets.
  • "Expand to full page" and "Show beside list" switch between the two views.
  • The URL records the open panel: a direct link opens the full-page editor.
  • Focus moves into the panel when it opens and returns to the list row when it closes. The drawer traps focus.

Some of the audit fixes are visible in E. Admins can't grant the Owner role. API keys can never be Owner. Disabled templates are hidden from Add device. Rules that switch hardware must keep a hold time, hysteresis and a cooldown. Viewers get read-only panels and no API keys page.

Dashboards follow the code's model. A dashboard is a personal record: a name plus a widget layout. Every member manages their own, with no admin gating. Widgets come in the 5 real types. Editing works as in the current app, on the dashboard itself. Edit layout shows × to remove a widget, arrows and drag to reorder, and a width control. Add widget opens a short form (type, device, metric, min/max for gauges). Changes save as you go. Rename, Duplicate and Delete sit in the ⋮ menu. Widgets whose metric no longer exists say so instead of rendering empty.

Version F (demo E is kept as it was) refines the full-page editors after comparing B’s stepper with E’s sections. Wide screens get a pinned section list with descriptions, counts and error badges. Steps are numbered, with ✓ once valid, only when creating. Forms are capped at about 760 px, with short fields side by side. Rows show an “Edit” hint, and there’s Expand all / Collapse all (open by default for three rows or fewer on a full page). A line under the title says what saving does, and Duplicate is a visible button. It applies to the template, device, rule, member and API key editors.

Version G: rule editor rework (F is kept as it was; open G). Recipes: “New rule” starts from recipes for the chosen device (too hot → fan, door open, humidity low, irrigate when dry, stop pump when the tank is low, device offline, schedule, or blank). New rules then read as numbered When / Then / Safety / Name. Workbench: the form sits beside a sticky preview with a 24-hour replay (“would have fired 2× at 09:45, 10:45”), the exact command it would send, live safety checks, other rules on the same actuator, a dry run with live readings, and “Try other values”. The Simulate tab is gone. Editable sentence: any condition or action phrase opens a small editor in place. Also: safety errors appear as you type; each save records a version with what changed, and any version can be restored; the save toast summarises the changes; the Rules list shows a 24-hour firing strip and “shares fan1” warnings; Reset latch shows the current readings and whether the rule will fire again.

UX review fixes (version F). A senior review graded F B+ (82/100): strong consistency and safety, weaker on phones and learnability. P1 fixes: on phones the editor header stacks, with tools above the title, and hides “Show beside list” and “Expand” below 1100 px, where no side panel exists. Tables become two-line items on phones (name and zone, then status, reading and last seen), so identifiers never break mid-word. Touch devices always show row chevrons and the “Edit” cue, and get 42 px icon buttons and 20 px checkboxes. P2 fixes: the rule editor shows one-time “Three steps to a rule” tips, “Edit logic” became “Edit rule”, and Ladder is marked as the expert view. Dashboard cards centre their value, the gauge shows its unit beside the number, and footers line up. The minimum text size is now 12.5 px (13 px on phones). Expected grade with these fixes: about A− (90).

Landing page (version F). The hero is text only, over the live device network. The control-loop log moved into Onboarding, where it shows what happens after the board is flashed. Plans became Deployment: Cloud (shared, hosted by iodriven), Dedicated cloud (single-tenant, operated by iodriven) and On-premise (single-tenant on the customer’s own server with Docker Compose), with a comparison table and notes on edge connectors and moving between options. Dedicated cloud and On-premise open a short “Talk to us” form (demo only, nothing is sent). The plan tiers are gone; retention and the device-contract topics moved to the FAQ.

Zones (version F, proposal). Zones aren’t in the backend today; the demo’s device “zone” was free text. F adds a deliberately simple Zones catalog under Configure. The list has search, All / In use / Empty filters, and each zone’s device count and status. The editor has only a name and notes; renaming updates the zone shown on its devices. A device changes zone only from its own settings (the zone dropdown in Edit device). Deleting a zone that still has devices is blocked, with a link to those devices, the same way an in-use template is blocked. The device list gains a zone filter, and the zone on a device page opens the zone. A real version needs a zones table with tenant_id and an RLS policy, with devices referencing it by foreign key.

One system across every screen. A consistency pass unified what had grown per feature. Choosing between options: one option-card look for rule behaviour and trigger, member role, Connect options and widget type. Badges: status pills for state (Online, Armed, Latched, Active, Invited, Enabled) and neutral tags for categories such as roles. Full pages: one layout (breadcrumb, page header, plain sections, a save bar that stays at the bottom of the window) for full-page editors, the rule editor, Connect and Settings. Lists: one toolbar everywhere (search, quick filters with counts, optional extra filter), a count footer, ⋮ on every row, and a hover hint that tells a panel row (“Open”) from a page row (“→”). Saving: records save explicitly with Discard and a leave warning (Settings now included); layouts and toggles apply at once with Undo. Colour: teal always means data and indigo always means controls. The landing page and the app share one primary button.

Connect device. Adding a device, or Get firmware on an existing one, opens a four-step page. 1 Credential: shown once, or a warning that getting firmware rotates it. 2 Firmware: board, Wi-Fi (BLE provisioning or typed in), TLS or plain, an editable pin map with clash checks, and a highlighted preview of the generated sketch. The preview follows the real firmware-sketch.ts structure, masks the credential, and Copy includes it in full. 3 Flash and Wi-Fi: Arduino IDE steps, BLE pairing steps and the expected Serial Monitor output. 4 Live check: status, config, the first reading per metric and a command test per actuator turn green on their own, with a hint for each item that’s still waiting.

Landing page. The demo now opens on iodriven.tech, rebuilt in the same design language. The hero reuses the network animation next to a live control-loop log (reading, rule fires, command, acknowledgement, clear), with the four numbers the product is built around: under 2 s required, under 500 ms typical, 500–1,000 devices per host, and 10 minutes to live data. A product tour renders the demo’s real Dashboards, Devices, Rules and Templates screens. The page then covers the hot and storage paths, safety defaults, onboarding with the device contract, security and operations, plans by retention (7 and 90 days; no prices, because the code has none), and an FAQ. Every call to action goes through sign-in into the demo, and “Open Rules in the demo” lands on Rules.

Sign-in. A brand panel shows the product at work: a live network of the workspace's devices sending readings to the in-memory rule engine, with commands going back to actuators and a few live readouts. The form has field errors, a single generic credentials error, show/hide password and a busy state. After sign-in you choose a workspace, since a person can belong to several.

Rules have two layouts. The panel is for checking a rule: its sentence, live state (armed, firing or latched), a read-only outline, and hold time and cooldown. Edit logic opens the full-page editor with Logic, Simulate and Activity tabs. Logic has a Form view (ALL/ANY groups with one-line condition and action rows) and a Ladder view (rung, parallel branches, timer, coils, and an inspector). Both views edit the same draft, and selecting a phrase in the sentence selects that condition. Simulate runs the unsaved draft against typed values or a 24-hour replay. Behaviour cards show Re-arm and Latch as timelines. Saving a rule that is live, latched or changing actuator targets asks for confirmation first.

Recommendation

Build on A: it fixes the structural problems without a rebrand and keeps the app consistent with the iodriven landing page. Take two pieces from the others: the ⌘K palette and Admin nav group from B, and j/k navigation with sparkline columns from C as an optional dense view on Devices. Use B's stepper only for first-run flows such as a template's first creation or Add device.

Suggested order of work

Each step is its own PR. Step 1 has no dependency on a direction and can start now.

  1. P0 CRUD fixesKey freeze, key pattern and reserved keys on actuators, disabled-template check, owner-role guard, key usage endpoint. Commits touching the catalog are tagged [core].
  2. API client error mappingParse 422 detail[] into {path: message} and expose it on ApiRequestError.
  3. PrimitivesToast, Dialog, Sheet, Switch, SecretReveal, CopyField, InlineEdit, DataTable, Button danger/icon. Replace the 4 secret boxes and 18 label copies.
  4. ShellGrouped nav, workspace chip, breadcrumbs, ⌘K, content max-width, route-level loading/error/not-found, a can() helper.
  5. Templates moduleSheet editor with draft validation, usage warnings, Review, dirty guard. This is the demo flow.
  6. Devices, then Rules, Dashboards and SettingsMigrate one module per PR onto DataTable and the page template, and delete the copied markup as you go.
